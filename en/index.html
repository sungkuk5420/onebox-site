AI inventory management for resellers

One warehouse ledger.
AI that catches double-selling first.

Korean sneaker and fashion resellers list the same pair on several marketplaces at once. When it sells on one, the listing on the others stays live. ONEBOX keeps a single ledger of what is physically in the warehouse and flags the overlap before the second order arrives.

At a glance

  • Who: individual and small-team resellers on KREAM, POIZON, MUSINSA and SOLDOUT (Korea's main resale marketplaces).
  • Problem: one pair, several live listings, one warehouse. A second sale means a cancellation penalty and account trust loss.
  • Product: SKU-level ledger (model code + size), receiving/shipping/adjustment history, stock counts, barcode, Excel import, plus AI alerts and suggested actions.
  • Status: ledger in beta on top of NANBA ONE (v1.33, in production). AI layer built on Anthropic Claude, in beta.

Product

Ledger, alerts, marketplace sync

Inventory is not tied to any marketplace. You can register, receive and count stock without logging into any platform. Marketplace listings are a layer on top of the ledger.

SKU ledger

The unit of stock is model code + size. Quantities are never stored as counters; they are folded from an append-only ledger, so the number on screen always has a traceable history.

Alerts that fit resale

No "low stock" noise (zero stock is normal in resale). Instead: over-exposed (more live listings than units), zero exposure, aging stock, and idle consignment stock at KREAM's warehouse.

Sale detection and delisting

Sales on KREAM are detected about once a minute and posted to the ledger. Delisting the overlapping listing is suggest-first; automatic mode runs only when every safety gate passes.

ONEBOX AI · built on Claude

Rules count the numbers. Claude explains and proposes.

The rule engine decides what is over-exposed. Claude turns that into a plain-language explanation and a recommended action, and reads the messy purchase records resellers actually have. Execution is always approved by a person.

Beta

Purchase records → structured SKUs

Resellers keep purchase records as spreadsheets, chat messages and photos of invoices. Claude reads them and returns model code, size, quantity and unit cost for review before receiving.

Beta

Alert explanation and next action

Instead of "CW2288-111 / 270 / over by 1", the user sees which channel sold when, and which listing is safest to pull, with the evidence. Suggest only; execute after approval.

Planned

Natural-language inventory questions

"How many Dunk Low 270 received last month are still unsold?" Claude translates the question into a ledger query. Quantities always come from the ledger fold, never from the model.

Planned

Product-name normalization

The same shoe is named differently on every marketplace. Claude maps variants to one model code so the ledger never shows the same pair as two rows.

Why Claude

This is money-bearing data. We need long context for full purchase histories, multimodal input for tables and invoice photos, and a model that says "I don't know" rather than guessing a quantity. Counting stays in the ledger; the model never writes to it.

What the AI does not do

  • Estimate quantities or edit the ledger. The ledger is the only producer of stock numbers.
  • Execute irreversible writes (cancel a listing, ship an order) on its own.
  • See marketplace tokens or passwords. Those never leave the user's PC.

Data principles

Marketplace credentials (tokens, cookies, passwords, OTP codes) are stored only inside the user's desktop app and are never sent to our servers, our database or the AI. The server sends commands to the PC and receives only secret-free responses. Stock quantities are computed from an append-only ledger.
